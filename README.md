# POS (KPO_dz2)- выполнил Величко Дмитрий БПИ257

## 1. Описание проекта и предметной области

ПОС — консольное приложение для учёта оценок студентов по заданным критериям. Позволяет вести список студентов, формировать рубрикатор оценивания, выставлять и изменять оценки, рассчитывать итоговый результат с учётом весов критериев, импортировать оценки из CSV и JSON и экспортировать результаты.

## 2. Ubiquitous Language

В проекте используется единый язык предметной области:

- **Студент (Student)** — человек, чьи результаты оцениваются.
- **Критерий (Criterion)** — параметр оценивания с максимальным баллом и весом.
- **Рубрикатор (Rubricator)** — набор критериев, используемых для оценивания.
- **Оценка (Evaluation)** — балл студента по определённому критерию, содержащий дату и комментарий.
- **Итог (Result)** — вычисляемый результат студента на основании оценок и весов критериев.

## 3. Entities и Value Objects

### Entities

| Entity | Описание |
|---|---|
| `Student` | Студент с уникальным ID и именем |
| `Criterion` | Критерий с уникальным ID, названием, максимальным баллом и весом |
| `Evaluation` | Оценка, идентифицируемая парой StudentId и CriterionId |

Сущности имеют идентичность и методы изменения своих свойств, которые проверяют допустимость данных.

### Value Objects

| Value Object | Описание | Ограничения |
|---|---|---|
| `Score` | Балл | Неотрицательное значение |
| `Weight` | Вес критерия | От 0 до 1 включительно |

Value Objects используются для представления значений с ограничениями, чтобы не работать с произвольными числами во всей доменной модели.

## 4. Инварианты

Доменная модель обеспечивает соблюдение основных правил:

- ID сущностей не должен быть пустым.
- Имя студента должно соответствовать допустимому формату.
- Название критерия должно быть допустимым.
- Максимальный балл критерия должен быть неотрицательным.
- Вес критерия находится в диапазоне от 0 до 1.
- Оценка не может быть отрицательной или превышать максимальный балл критерия.
- Нельзя добавить критерий с уже существующим названием в рубрикатор.
- Итог вычисляется на основании оценок и весов критериев, а не хранится как произвольное значение.

Проверки выполняются при создании и изменении сущностей, а также в сценариях приложения, взаимодействующих с доменной моделью.

## 5. Границы агрегатов

В качестве основных границ модели выделены:

- **Student** — самостоятельная сущность, идентифицируемая собственным ID.
- **Criterion** — самостоятельная сущность, определяющая правила оценивания.
- **Evaluation** — отдельная запись, связывающая студента и критерий через их идентификаторы.
- **Rubricator** — объект, управляющий набором критериев, проверяющий их уникальность и обеспечивающий операции добавления, удаления и поиска.

Оценка хранит идентификаторы студента и критерия, а не сами объекты, что позволяет разделить жизненный цикл этих сущностей.

Рубрикатор выступает точкой управления набором критериев, а студент и критерий не зависят от конкретного способа хранения данных.

## 6. Архитектура

В проекте используется архитектурный подход **Ports & Adapters (Hexagonal Architecture)** с разделением на слои.

### Domain

Содержит бизнес-модель и правила предметной области:

- `entities` — Student, Criterion, Evaluation, Rubricator;
- `valueobjects` — Score, Weight;
- `services` — ResultEvalCalcService;
- `interfaces` — интерфейсы репозиториев.

Domain не зависит от консольного интерфейса, JSON-файлов или инфраструктурных библиотек.

### Application

Организует сценарии использования приложения:

- добавление, изменение, удаление и получение данных;
- расчёт итогового результата;
- импорт и экспорт оценок.

Содержит Use Cases, модели передачи данных и интерфейсы для импортёров, экспортёров и фабрики импортёров.

### Infrastructure

Реализует внешние механизмы:

- репозитории с хранением данных в JSON;
- CSV- и JSON-импортёры;
- фабрику импортёров;
- CSV-экспорт результатов.

### Presentation

Реализован классом `ConsoleMenu`. Отвечает за вывод меню, ввод пользователя, проверку формата данных, вызов Use Cases и отображение результатов.

### Composition Root

`Program.cs` регистрирует зависимости в DI-контейнере, связывает интерфейсы с конкретными реализациями и запускает консольное приложение.

Направление зависимостей организовано внутрь: Application использует Domain и его абстракции, Infrastructure реализует интерфейсы внутренних слоёв, а Program.cs связывает компоненты при запуске.

## 7. GoF-паттерны

### Factory — Simple Factory

`EvaluationImporterFactory` выбирает импортёр в зависимости от расширения файла. Фабрика получает набор реализаций `IEvaluationImporter` и возвращает подходящий объект для CSV или JSON.

### Strategy — вариативность алгоритма расчёта

`ResultEvalCalcService` содержит два варианта вычисления результата:

- V1 — округление итогового значения после суммирования;
- V2 — округление каждого слагаемого перед суммированием.

Выбор алгоритма осуществляется через параметр стратегии. В текущей реализации алгоритмы находятся внутри одного сервиса, поэтому решение использует идею Strategy, но не классическую структуру паттерна с отдельными классами стратегий.

## 8. Инструкция запуска

### Требования

- .NET SDK 8.0 или новее, поддерживающий сборку под `net8.0`.

### Запуск

Из директории проекта, в которой находится `POS.csproj`:

```bash
dotnet restore
dotnet run
```

При запуске приложение использует JSON-файлы:

- `students.json` — студенты;
- `rubricator.json` — критерии;
- `evaluations.json` — оценки.
